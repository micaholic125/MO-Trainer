# 08 联机模式设计思路（S7）

> 状态：**设计稿** ｜ 建立 2026-10-23 ｜ **本轮不改任何代码**
> 关联：`docs/01` FR-08、`docs/02` §9、`docs/04` S7、`CLAUDE.md` §4.6
> 一句话结论：**先做「联机安全模式」，不做「假同步」。**
> 真正让所有电脑同步作弊，在帧同步游戏里无法保证；等两台机器实测之后，再决定要不要做广播。

---

## 0. 给非技术读者的三句话

1. 联机游戏像「几台电脑各跑一份一模一样的录像」：大家只交换你点了什么，各自算出一模一样的世界。
2. 我们的修改器是**从外面改录像里的数字**。只要几台电脑改的时刻差了一帧，录像就对不上，
   游戏会判「不同步（out of sync）」并把房间里的人踢掉。
3. 所以联机时最该做的**不是**"想办法同步"，而是**把会踢人的操作默认锁起来**，
   并且让你每次都能看清自己在哪个模式、哪些功能是锁着的。

---

## 1. 技术事实：为什么「全员同步」保证不了

| 事实 | 对设计的影响 |
| --- | --- |
| RA2/YR 是**帧同步（lockstep）确定性模拟**：每个客户端独立跑完整模拟，只交换指令，引擎周期性比对校验和 | 任何"参与模拟的状态"（血量、金钱、生产进度、电力）被单方面改动，迟早会被校验抓到 → out of sync |
| 我们的工具是**外部进程**，靠轮询内存决定何时写 | 无法保证两台电脑在**同一逻辑帧**写入；轮询间隔、网卡、系统调度都会带来几毫秒到几十毫秒的差 |
| UDP 广播也有延迟与丢包 | 即使所有客户端都收到同一条指令，应用时刻仍可能差几帧 |
| 校验和是周期性的，不是每帧都比 | 有些差异可能短暂"看不出来"，但只要状态不复原，迟早会掉；不能拿"撑了几分钟"当安全证据 |

**结论**：
- 「全员同步模式」最多只能叫**尽力同步**，**不能承诺不掉线**。
- 原规划里唯一有希望联机安全的功能是**全图视野**（主要影响本机渲染），
  它已在 2026-10-17 决定不做。剩下五个功能**都会改模拟状态**。
- 因此：**本阶段不写网络代码**。先把"会掉线"的操作管住，再用两台机器实测，才知道广播值不值得做。

## 3. 三种模式怎么定义（建议）

不要按"是不是局域网"分，而要按**房间里有没有其他真人玩家**分 —— 局域网里只有你和 AI 时，
没有第二个客户端可掉线，作弊是安全的；这个区分对玩家更有用。

| 模式 | 适用场景 | 工具行为 | 技术保证 |
| --- | --- | --- | --- |
| **单人 / 只有我一个真人**（默认） | 单人战役、遭遇战打 AI、局域网里只有我 + AI | 全部功能开放，保留现有高风险勾选 | 不需要同步，安全 |
| **房间里有其他真人**（联机安全模式） | 和真人联机（含组队打 AI） | **默认锁死全部会改游戏状态的功能**；逐项二次确认后才能开；状态条常驻红色提示 | **不保证**；工具只能减少误操作，不能防止不同步 |
| **全员同步（实验性）** | 所有玩家都装同一版本、都同意 | 房主广播开关与目标值；客户端在尽量接近的时刻应用 | **仅降低概率**；本阶段**不实现**，等实测 |

> **模式名称**：界面上建议写"这局有没有其他真人玩家？"而不是"单人 / 联机"，
> 因为"联机打 AI"这个场景很容易被误解成危险模式。

## 4. 联机安全模式：默认策略（需要你拍板）

联机安全模式的核心不是"让作弊能用"，而是**默认什么都不改**。有两种策略：

### 策略 A：保守（推荐）

**只要房间里还有其他真人，默认锁死全部五项会改状态的功能**（金钱、电力、无敌、秒杀、瞬间建造）。
每一项都可以由玩家**逐项**解锁，解锁时必须勾选一句专门的确认：

> 「我知道这会让房间里其他玩家可能掉线；这局只有我和 AI 除外。」

- 好处：在没有任何实测数据之前，不会因为"电力标了低风险"就把危险项放出去。
- 代价：联机时想用任何功能都要多点一次；但这正是"友好模式"该有的摩擦。
- 等 S7-B 实测出"哪个功能真的不掉线"之后，再把安全的项降级为默认可用。

### 策略 B：按现有分级

只锁高风险的三项（无敌 / 秒杀 / 瞬间建造）；金钱（中）和电力（低）默认可用，只给提示。

- 好处：少点几下。
- 代价：**电力的"低"很可能是错的**；金钱是否参与校验也没实测。一旦判断错，就是把人踢下线。
- 不推荐在实测前使用。

> 无论选哪种，**引擎层都要有闸门**：不能只靠界面把按钮变灰。
> 实现时在 `CheatEngine.ApplyAll` 里加一道"联机模式 + 高风险 + 未解锁 → 一个字节都不写"的检查，
> 并写日志说明原因。这样即使界面或热键有 bug，也不会写错内存。

## 5. 本阶段（S7-A）到底做什么

### 5.1 范围（一句话）

**只做「联机安全模式」：模式选择 + 引擎闸门 + 风险提示 + 自检。一行网络代码都不写。**

### 5.2 必须交付

1. **模式选择**
   - 「这局有没有其他真人玩家？」两个选项：`只有我 / 有其他人`。
   - 会话级，不落盘（与现有"运行模式不持久化"一致）。
   - **启动顺序：先选模式，再启动锁定线程** —— 保证在用户选完之前，一个字节都不写。
     否则上一局记住的"金钱自动开"会先写进去，等用户再选联机模式时已经晚了。
   - **联机模式下不自动恢复任何功能（包括金钱）**；金钱的自动恢复只在"只有我"模式下生效。
   - 切到联机模式时：**强制关闭全部已开启的功能**、**清空全部高风险确认**，并写日志。
     不是"拦住新的开启"就完事 —— 已经开着的必须当场关掉。
2. **引擎级闸门**
   - `CheatEngine` 知道当前模式；**模式未选定前不写任何功能**。
   - 联机模式 + 高风险 + 未解锁 → 拒绝写入，`LastError` 写明原因。
   - 热键、界面、任何未来入口都走同一道闸门。
3. **风险提示**
   - 联机模式下，功能卡片按风险着色，锁定项写明"为什么锁、怎么解锁"。
   - 状态条常驻：`模式：有其他人｜高风险已锁`；公网 CnCNet 禁用声明常驻。
   - 解锁时使用联机专用确认文案（不是现在那句泛泛的"联机不同步"）。
4. **电力分级纠正**
   - 把电力从 `Low` 改为 `High`（或至少 `Medium`），理由写进代码注释与文档。
   - 这一条即使不选策略 A 也必须做，否则安全模式会把电力当安全项。
5. **自检**（新增至少 6 条断言）
   - 单人模式下一切行为与现在完全一致（回归）。
   - 联机模式 + 高风险 + 未解锁 → 引擎拒绝写、内存一个字节没变。
   - 联机模式 + 高风险 + 已解锁 → 允许（如果策略允许解锁）。
   - 切换模式会清空确认。
   - 热键路径不能绕过闸门。
   - 电力的风险等级不再是 Low。
6. **文档**
   - `docs/01` FR-08 与 `docs/02` §9 同步更新（含电力分级纠正）。
   - `docs/04` S7 步骤重排（见 §6）。
   - 使用说明的"联机"章节（S8 会直接用）。

### 5.3 明确不做

- 不做 UDP 广播 / 同步协议（等 S7-C）。
- 不做"同步状态"指示灯 —— 没有真实同步，就不能给假指示。
- 不自动识别"房间里有没有其他真人"（除非将来找到可靠的引擎标志，见 §8）。
- 不承诺"不掉线"；文档与界面都必须写明"仅降低误操作，不能防止不同步"。
- 不在公网 CnCNet 使用。

### 5.4 验收标准

- 单人模式下，五项功能行为与 2026-10-23 的版本**完全一致**（自检回归）。
- **启动时先选模式；选"有其他人"后，金钱不会自动开，已开着的功能被强制关闭并记日志。**
- 切到"有其他人"后：高风险项默认锁死；点击、热键都开不了；日志写明拒绝原因。
- 解锁后能开，但每次切换模式都要重新确认。
- 关闭再打开程序，模式回到默认（不记忆）。
- 自检全绿，改坏验证至少 2 处精确转红。

## 6. 整个 S7 的推进顺序（建议重排）

原来的 S7-1～S7-4 是"先协议、再实测"，本设计建议改成"先安全、再实测、最后才协议"：

| 编号 | 内容 | 需要什么 | 产出 |
| --- | --- | --- | --- |
| **S7-A**（本阶段） | 联机安全模式（本文 §5） | 不需要游戏 | 模式 + 闸门 + 提示 + 自检 |
| **S7-B** | **两台机器实测**：逐项测哪些功能真的掉线 | 两台电脑 + 一次局域网对局 | 一张"功能 × 是否掉线"的实测表 |
| **S7-C**（条件） | 只对实测证明"能撑住"的功能做 UDP 广播 | 取决于 S7-B 结果 | 实验性同步，明确标注 |
| **S7-D** | 文档与使用说明定稿 | — | 联机章节 |

**S7-B 的实测表**（建议至少跑这些局）：

| 局 | 谁开 | 开什么 | 观察 |
| --- | --- | --- | --- |
| 1 | 都不开（只运行工具） | 无 | 基线：确认工具本身不导致掉线 |
| 2 | 房主单方 | 金钱 | 是否掉线、多久掉、日志 |
| 3 | 双方都开 | 金钱 | 与第 2 局对比 |
| 4 | 房主单方 | 电力 | 电力到底是不是"低风险" |
| 5 | 房主单方 | 无敌 / 秒杀 / 瞬间建造 | 预期会掉线，确认现象 |

> 只有某一项在**至少 3 局**里都不掉线，才值得为它做广播。
> 如果全部掉线，就正式写"全员同步不可行"，S7 只保留安全模式 —— 这也是一种合格的交付。

## 7. 如果将来做「全员同步」（S7-C 草案，暂不实施）

### 7.1 角色与流程

- 房主：唯一能下指令的人；维护房间成员列表。
- 客户端：只应用房主广播的指令，不允许自行修改。
- 所有玩家必须运行**同一构建**、**同一校准指纹**（游戏 CRC `0x1B499086` + 模块大小）。
- 任何一项不一致 → 拒绝加入，并说明原因。

### 7.2 报文草案（UDP，仅局域网）

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| magic | 4 | `MOT1` |
| version | 2 | 协议版本 |
| type | 1 | HELLO / HEARTBEAT / COMMAND / ACK / BYE |
| sessionId | 4 | 房主随机生成 |
| sequence | 4 | 指令序号，防重复 |
| featureId | 1 | 功能编号 |
| value | 4 | 目标值 |
| targetFrame | 4 | 期望应用的逻辑帧（0 = 尽快） |
| gameCrc | 4 | 游戏版本指纹 |
| profileHash | 4 | 校准配置指纹 |
| checksum | 2 | 报文校验 |

- 默认端口建议 `27015`，仅绑定局域网广播地址；不访问公网。
- 指令连发 3 次；客户端按 `sequence` 去重。
- 心跳 1 秒一次；3 秒没心跳视为掉线，界面显示。
- **不显示"已同步"**，只显示"已连接 N 台 / 最后一条指令"。

### 7.3 为什么它仍可能失败

- 无法保证 `targetFrame` 在所有客户端都落在同一帧（轮询 + 网络抖动）。
- 只要有一台没装工具，它就会掉线。
- 改的是模拟状态，任何时序差都可能改变 AI 决策、单位死亡顺序、金钱结算。
- 因此措辞必须是"实验性 / 可能掉线"，不能写"同步模式"。

## 8. 未解决的问题（需要实测或后续研究）

1. **能否可靠识别"房间里有没有其他真人玩家"？**
   如果能找到引擎里的房间/会话标志，安全模式可以自动切换，避免用户忘记。
   目前**没有验证过**，所以先用手动选择；找到并验证后再自动提示。
2. **金钱到底参不参与同步校验？** 只能实测。
3. **电力的真实同步影响？** 只能实测；在数据出来前按高风险处理。
4. **局域网里只有我 + AI 时，工具是否会因为"网络模式"产生额外校验？**
   理论上是单客户端，无对比对象；仍建议在 S7-B 第 1 局顺带确认。
