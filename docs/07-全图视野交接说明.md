## 五、**判据本身**的三个硬伤（做这件事的人必须先看这一节）

这三条是 2026-10-13 一整天用真机换来的，**不看你就会重走**。

### 5.1 快照工具默认漏掉一整类内存

`tools\MemSnap.cs` 默认只收**可写**区域；带 `all` 才收只读区域。同一局实测：
默认 **520 区域 / 293 MB**，带 `all` **770 区域 / 363 MB**（差 250 区域 / 70 MB）。
它还会主动跳过**可执行**页 —— 老游戏的图形缓冲常被标成"可写又可执行"，那也是一块从没看过的地方。
**此前十几轮跑的全是默认档。**

### 5.2 ⚠ "找连续变化的一整段"这个判据，其实在测"有没有东西在动"

这是最大的一个坑，务必读完：

- "连续 ≥12 字节、同一拍朝同一方向变、前后取值齐整" —— 这套筛子**非常利**，539 MB 里只剩个位数处。
- 用户探路时它确实亮了 9 处，而且**只**在探路那 40 秒里亮。
- **但设计了一次辨别实验**：让用户**只在已经亮着的地方来回走、绝不探新地方** —— **照样亮 8 处，而且在同一片内存里**。
- ⇒ 它是**"有单位在动"的副产品**（单位动画 / 特效对象被创建），**不是"地图被点亮"的产物**。

**根因**：**新分配出来的一块内存整块都是同一个值**，在字节层面和"一整片格子一起翻转"**完全无法区分**。
**下一个人做任何"找整段变化"的判据，都必须先回答"这是新分配的内存，还是既有数据被改写"。**

### 5.3 别把"只出现一次"的候选丢掉

第一版差分报告只打印"出现过 ≥2 次"的候选，于是那次找到的 5 处**单次**现象被自己的报告扔掉、事后无法复查。
**负面结果也是数据。**

### 10.2 黑幕的真实结构（字段语义来自 `CellClass.h` 原注释）

```
0x0087F7E8        MapClass 实例（.data 里的全局对象，非指针）
  +0x13C          Cells 的 Items 指针  -> CellClass* 指针数组（堆）
  +0x140          Cells 的 Capacity（= 0x40000 = 262144，恒定）
CellClass（每格一个堆对象，大小 0x148）：
  +0x00           vtable（0x007E88C8 一带，模块内）
  +0x24 / +0x26   X / Y（short，格子自报坐标）
  +0x120          Shroudedness（char）0xFE=黑, 0xFF=可见, 0..48=渐入渐出动画帧
  +0x121          Foggedness（char）同一套取值
下标公式：idx = (Y << 9) + X    （MapClass::GetCellIndex）
```

**为什么 13 轮全空**：黑幕**不是一张表**，是 10527 个**散落堆里的独立对象**各自带
一个字节。既无连续段（10 号假设找的），也无统一步长（相邻格子差 4 字节——但对象在堆里
散布，**没有线性主步长**），值也不统一（FE / FF / 动画帧混布）。第三节那 10 类判据
**从构造上就不可能看见它** —— 不是筛子不够利，是靶子不在那类形状里。

另：`0x87F8DC`（二、环境事实表里那条"引擎地图对象"）是**误认** —— 它是 MapClass
实例 `+0xF4` 处的**地图宽度**字段（当晚读出 61，与 MapRect 一致），不是对象本体。

### 10.3 验证（两个独立样本，判据都是"自报坐标 vs 数组下标"这个等式，随机数据不可能吻合）

### 10.4 实现路线（下一步，未动工）

**写入目标：把地图内每个格子对象的 `+0x120`（和 `+0x121`）从 0xFE 写成 0xFF。**

1. 走 `0x87F7E8 → +0x13C` 拿格子指针数组，遍历 262144 槽（当次会话实际非空 ≈ 1 万）
2. 每个非空指针先过三关：虚表在模块内、`idx == (Y<<9)+X` 等式成立、地址可写
   （`VirtualQueryEx`）—— **三关全过才写**，单格失败跳过并记日志，绝不停机
3. 只写 `0xFE`→`0xFF`（已是 0xFF / 动画帧的不动，把"半亮"格子留在动画里更自然）
4. 写完一次后，后续每拍**只补差量**（新翻黑的格子），不重复全量写
5. `TechnoOps.RevealMap` 里已写好的"分片 / 游标 / 缺数据拒绝执行"骨架直接复用

**风险与边界**：
- 不会碰 `.text`、不注入 —— 写的全是堆上格子对象的数据字节，符合技术红线
- 空军视野 / 双层迷雾（用户领域知识：临时层 + 永久层）—— `Shroudedness` 是**每玩家**的吗？

### 11.1 现在确定知道什么（全部已核实）

**格子层链路完全可靠**（第十节的内容全部站住了）：

```
0x0087F7E8 (MapClass 实例) → +0x13C (Cells.Items) → CellClass* 数组
每格 +0x24/+0x26 = X/Y；+0x120 = Shroudedness；+0x130 = Flags（bit3 = cf_Explored）
idx = (Y<<9)+X；两道闸（虚表在模块内 + 坐标-下标等式）能 100% 过滤
`tools\HousePeek.exe map` = 只读迷雾图打印，已真机验收（10527/10527 全过）
```

**但格子层不是渲染的依据。** 三个写入实验（用户逐个批准、全部写入+读回成功）：

| # | 写了什么 | 引擎的反应 | 屏幕 |
| --- | --- | --- | --- |
| 1 | 每黑格 `+0x120` 0xFE→0xFF（8127 格） | **下一拍整批抹回 0xFE** | 无变化 |
| 2 | 每格 `Flags+0x130 \|= 0x08`（cf_Explored） | **保留不擦，但不消费** | 无变化 |
| 3 | 房子 `+0x240 Visionary` / `+0x241 MapIsClear` = 1 | **保留不擦**（16s 复查仍在） | 无变化 |

⇒ **渲染每拍读的是另一份"每家一份"的数据**（下称**账本**）。格子层的 `Shroudedness`
是引擎**算出来的影子**——账本变，影子跟着变；直接改影子没有意义。

**账本没找到，但已经把包围圈收得很紧**（详见 11.3）。

### 11.2 选项 B 事故（**必须先读，别再走**）

用户批准过一次"让游戏执行它自己的 `MapClass::Reveal`（`0x577D90`）"：
`CreateRemoteThread` + 挂起主线程 + 5 字节 stub。**结果：wait 超时（258=TIMEOUT）
→ 约 10 秒后游戏硬崩，连异常转储都没写**（进程被终结）。原因：引擎是多线程的
（渲染/声音/网络线程不归主线程管），`Reveal` 是全图级重活，远程触发撞上活跃线程。

- **损失**：那一局的进度。游戏本体/存档/配置/修改器：无损。
- **结论写死**：**全图级引擎函数永远不要从外面远程调用。这条路永久关闭。**
- 这与 10-13 白天两次"逐页乱戳弄崩游戏"是同一类错误的两个变体：
  **把"引擎函数看起来简单"当成"执行起来安全"。**

### 11.3 账本搜索——已排除与头号嫌疑

本轮新增排除（判据来源见 `tools\ShroudLIVE.cs` / `ShroudBook.cs` / `ShroudBook2.cs`
与 `开发日志/2026-10-13.md` 第 9 轮）：

1. **跨房共享指针**：三家房子（用户+2 AI，数组在 `0xA80228`，本局实测 3 家）里
   49 个"三家同值"的指针槽挖开**全是模块内虚表**——不是账本。
2. **房子 span 内嵌 21KB 平面**：三家房子的前 `0x5800` 字节里都没有
   `{0xFE,0xFF}` 主导的 21609 字节窗口。
